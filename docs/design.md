## 1. 背景・課題

### 1.1 誰が困っているのか

**主な対象：県外から進学でこの地域にやってきた大学生**

地域に溶け込みたい気持ちはあるが、以下の障壁によって参加の一歩が踏み出せずにいる。

| カテゴリ | 具体的な困りごと |
|---|---|
| 移動・孤立 | 日常の移動手段が限られていて、地域の人と繋がりをつくりにくい |
| 情報アクセス | イベントやボランティアを調べても、一人で飛び込む不安がある |
| 関係性の壁 | すでにできあがった関係性の中に後から入るのが気後れする |

「行きたい気持ちはある。でも一人じゃ不安。」—— この言葉が、このアプリが解決しようとしている問いの核心である。

### 1.2 2つの障壁

課題を整理すると、参加を阻んでいる要因は2つに絞られる。

1. **「知らない人と一緒に行く」不安** — 誰と行くかがわからないと最初の一歩が踏み出せない
2. **情報へのアクセスの難しさ** — イベント情報が分散していて、一人の大学生には見つけにくい

単なるイベント情報アプリでも、マッチングアプリでもない。**「不安を減らしながら、気持ちの合う人と一緒に地域に踏み出す」** ための場所が必要である。

## 2. アプリの思想・コンセプト

### 2.1 一言で言うと

> **「気持ちの合う人と一緒に、地域への最初の一歩を踏み出せる場所」**

### 2.2 設計の核となる思想

#### ① マッチングの核心は「動機・フィーリング」

誰と行くかを決める基準は、プロフィールや属性スペックではなく、**「なぜ行きたいか」という気持ちの共鳴**である。「同じ気持ちの人がいるなら行ける」という感覚を生み出すことが、参加への背中を押す。

旗の中心に「行きたい理由・気持ち」を置いているのはこの思想からである。

#### ② 「安心」は積み重ねによって育つ

初めて会う人への不安を一度に解消しようとするのは難しい。そのため、SNSアカウント連携（普段の投稿から人となりが伝わる）、参加履歴の公開（行動の積み重ねが信頼になる）、相互評価（実際に一緒に参加した人からの評価）という仕組みを通じて、**使い続けるほどに安心感が高まる設計**にする。

#### ③ シンプルさを守る：当日のやり取りはアプリ外で

アプリの役割は「一緒に行く人を見つける」ことまでである。遅刻連絡や待ち合わせの調整など、当日のコミュニケーションはSNSを通じて直接行う（本人の判断に委ねる）。チャット機能をあえて作らないことで、**アプリの目的を「出会いの場の提供」に絞り込む**。

#### ④ 「地域限定」を強みにする

使う人・場所を絞ることで、情報の質と安心感を保つ。広げすぎないことが、このサービスの信頼性の源泉になる。

### 2.3 目指す状態

- 気持ちの合う人と一緒にイベント・ボランティアに参加できるようになる
- 知らない人でも「この人となら安心」と感じられる
- 地域のイベント情報が自然と集まっていて、探しやすい
- 参加を重ねるうちに、地域の人との繋がりが自然と育っていく

## 3. 利用者定義

### 3.1 主な利用者

| 利用者 | 説明 |
|---|---|
| **大学生（主要ターゲット）** | 県外から進学でこの地域にやってきた学生。地域に関わりたいが一人では不安 |
| **地域に住む人（サブターゲット）** | 地域のイベントや活動に関心がある社会人・地域住民 |

### 3.2 登録情報

最低限の情報のみ。過度な個人情報は求めない。

- ニックネーム
- メールアドレス（任意）
- SNSアカウント（1つ、必須）

SNSアカウントを必須とするのは、「普段の投稿・人となりが伝わる」ことが「この人となら安心」という感覚を生む最も効果的な手段だからである。

### 3.3 アカウントの要否

| 行動 | Step 1 | Step 2以降 |
|---|---|---|
| イベント情報を見るだけ | 不要 | 不要 |
| 旗を立てる | 不要（ニックネームのみ） | アカウント必要 |
| 旗を探す・手を挙げる | 不要（ニックネームのみ） | アカウント必要 |

Step 1の目的は「旗を立てる・眺める体験を試す」こと。まず価値の核が機能するかを検証することを優先するため、アカウント機能はStep 2で実装する。

## 4. コアの仕組み：「旗」

### 4.1 「旗」とは何か

「旗」とは、行きたいイベントがあるけど不安を感じている人が、一緒に行ってくれる仲間を募るための **"ポスター"** のようなもの。

単なる「一緒に行く人募集」ではなく、**その人の動機・フィーリングが乗った宣言**である。「なぜ行きたいか」が書かれているから、読んだ人が「この人と一緒に行きたいかどうか」をフィーリングで判断できる。

### 4.2 旗に含まれる情報

| 項目 | 内容 | 備考 |
|---|---|---|
| 誰が立てているか | ニックネーム・SNSリンク・参加履歴 | 人となりが伝わる |
| 行きたいイベント | DBに登録されたイベント情報から選択 | 現時点は手動登録 |
| **行きたい理由・気持ち** | 不安度、温度感、コメント | **ここが一番大切** |
| 何人で行きたいか | 二人・三人・四人 | 二人が怖い人のために三人以上も選択肢に |
| 一緒に行きたい人の条件 | 性別（同性のみ／こだわらない）・属性（大学生限定／社会人可） | 絞りすぎない範囲で設定 |
| 集合情報 | 集合場所・日時・締め切り | 当日の直接連絡はSNSで |

> **参加人数について：** 「二人だと怖い」と感じる人がいることへの配慮から、三人以上の選択肢を残している。一対一の密な関係性が生じる可能性を下げ、気軽に参加できるグループの雰囲気を生み出す。

> **属性条件の絞り込みについて：** 年齢範囲や細かい地域指定は、条件を複雑にすることでマッチングが成立しにくくなるリスクがあるため、Step 1では性別・大学生/社会人の2軸のみに絞っている。

### 4.3 「旗」に手を挙げる〜当日のフロー

```
旗に手を挙げた人が出る → 旗を立てた人に通知
　↓
旗を立てた人がSNSを確認して承認 or 否認 → 相手に通知
　↓（承認人数が上限に達するか、締切日が来たら）
旗のステータスが「締切済」になる → 検討中のままの人に定型文通知
　↓
当日集合（当日の連絡はSNSで直接）
```

- アプリ上でのやり取りは、あえて機能としてしない（シンプルさのため）
- 当日の連絡（遅刻など）はSNSを通じて直接行う（本人の判断）

### 4.4 承認・締切のルール

**承認人数の定義：**
- 承認できる上限人数 = `group_size`（一緒に行く人数）− 1
- group_sizeは「自分を含めた人数」のため、旗を立てた人自身を除いた人数が上限になる
- 例：「三人で行きたい」の場合、承認できるのは最大2人

**締切の発動条件：**（どちらか先に来た方）
1. `deadline`（締切日）が来た
2. 承認人数が上限（group_size − 1）に達した

締切が発動すると旗のstatusが「締切済」に変わり、「検討中」のままの人全員に定型文通知が自動送信される。

**人数上限到達後の操作について：**
- 承認人数が上限に達した後に人数（group_size）を増やすことはできない
- 手を挙げた人に対して失礼になるため、後から上限を変更する操作は設計上禁止する

**旗の取り下げ：**
- 旗を立てた人は締切前であれば旗を取り下げることができる
- 取り下げ時は、手を挙げていた人全員（承認済み含む）に「旗が取り下げられました」と自動通知
- 取り下げ後は復元不可

**エントリーの取り下げ：**
- 手を挙げた人は締切前であれば取り下げできる
- 承認済みでも締切前なら取り下げ可能
- 承認済みの人が取り下げた場合、旗を立てた人に通知し、旗のstatusが「締切済」だった場合は「募集中」に戻る

### 4.5 「安心」を育てる仕組み

| 仕組み | 内容 | 実装ステップ |
|---|---|---|
| SNSアカウント連携 | 普段の投稿・人となりが伝わる。過度な個人情報は不要 | Step 1-B（アカウント実装時） |
| 参加履歴の公開 | 旗を立てた・集った履歴。行動の積み重ねが信頼になる | Step 2 |
| 一緒に行った人からの評価（相互） | 実際に一緒に参加した人からの「安心度」評価が蓄積 | Step 3 |

## 5. 利用フロー詳細

### 5.1 旗を探す（手を挙げる）フロー

```
トップページ
　↓「旗を探す」を選ぶ
Step1：不安度を選ぶ（初めてで不安 / 慣れている）
　↓
Step2：イベント種類と温度感を選ぶ
　　　 種類：ボランティア / 祭り・地域行事 / ワークショップ・体験
　　　 温度感：落ち着いて参加したい / ワイワイ参加したい
　↓
旗一覧ページ（条件に合った旗が並ぶ）
　↓ 気になる旗をタップ
旗詳細ページ（旗の情報・行きたい理由を確認）
　↓「手を挙げる」ボタン（SNS・ニックネーム・メッセージを入力）
手を挙げた完了ページ
```

> **フィルタリングの設計意図：** 不安度・イベント種類・温度感の3軸で絞り込む。スペックではなく「気持ち・状態」で絞り込むことで、フィーリングの合う旗にたどり着ける設計にしている。

### 5.2 旗を立てる（仲間を募る）フロー

```
トップページ
　↓「旗を立てる」を選ぶ
Step1：イベントを選ぶ（DBに登録済みのリストから選択）
　↓
Step2：気持ち・温度感を入力する（不安度・ワイワイ度・行きたい理由）
　↓
Step3：一緒に行きたい人の条件を選ぶ（人数・性別・属性）
　↓
Step4：集合場所・日時・締め切りを入力する
　↓
確認画面（入力内容の確認）
　↓「投稿する」
旗投稿完了ページ
```

### 5.3 旗の管理フロー（旗を立てた人）

**旗管理ページで旗を立てた人ができること：**

```
マイ旗ページ（立てた旗の一覧・手挙げ人数を確認）
　↓ 旗をタップ
旗管理ページ
　├── 手を挙げた人の一覧を確認
　│     ニックネーム・SNSアカウント・ひとこと・エントリー日時
　│
　├── 個別に承認する（締切前ならいつでも可）
　│     → 手を挙げた人に「承認されました」通知
　│     → 承認数が上限に達したら旗を自動締切
　│
　├── 個別に否認する（締切前ならいつでも可）
　│     → 手を挙げた人に「否認されました」通知
　│
　├── 手動で締め切る（締切日前でも実行可）
　│     → 検討中のままの人全員に定型文通知
　│
　└── 旗を取り下げる
　      → 手を挙げていた全員（承認済み含む）に通知
　      → 取り下げ後は復元不可
```

**手を挙げた人のアクション：**

```
旗詳細ページ
　↓ 手を挙げるフォームに入力（ニックネーム・SNS・ひとこと・メール）
手を挙げた完了ページ
　↓
マイエントリーページ（ステータス確認）
　├── 承認待ち：旗を立てた人が確認中
　├── 承認済み：当日はSNSで直接連絡
　├── 否認：別の旗を探す
　└── 取り下げ（締切前ならいつでも可・承認済みでも可）
　      → 旗を立てた人に通知
　      → 承認済みだった場合、旗が「募集中」に戻る場合あり
```

**システムが自動で行うこと：**

| トリガー | 処理 |
|---|---|
| 締切日が来た | statusを「締切済」に変更・検討中の人全員に定型文通知 |
| 承認数が上限に達した | statusを「締切済」に変更・検討中の人全員に定型文通知 |
| 承認済みの人が取り下げた（締切済だった場合） | statusを「募集中」に戻す・旗を立てた人に通知 |

## 7. 意図的に作らないもの（除外機能）

除外の判断には明確な理由がある。

| 除外機能 | 除外の理由 |
|---|---|
| **チャット・メッセージ機能** | アプリの役割を「出会いの場の提供」に絞るため。当日のやり取りはSNSで十分。メッセージ機能を作るとアプリが「コミュニケーションツール」になり、本来の目的がぼやける |
| **アカウント機能（Step 1）** | Step 1の目的は「旗を立てる・眺める体験を試す」こと。認証の複雑さを持ち込む前に、まず価値の核が機能するかを検証する |
| **年齢範囲・地域の細かい絞り込み** | 条件を複雑にするとマッチングが成立しにくくなる。参加のハードルを上げない |
| **イベント情報の自動収集** | Step 1〜3でユーザーの反応を見てから実装する。技術的コストが高い割に、初期フェーズでは手動登録で十分 |
| **評価機能（Step 1・2）** | 参加実績が積み上がってから意味を持つ機能。最初から作っても機能しない |

| デプロイ | Render | GitHubと連携した自動デプロイ・無料枠あり。個人開発の最初期に適切 |
| バージョン管理 | GitHub | 標準的。Renderとの連携も容易 |

## 12. 開発体制・開発方針

### 12.1 体制

**1人開発（claude.ai + Claude Codeを使い分ける）**

| ツール | 役割 | 使うタイミング |
|---|---|---|
| **claude.ai（Webスレッド）** | 「何を作るか」を決める | 設計・仕様決定・技術選定の相談・詰まったときの原因調査 |
| **Claude Code（ターミナル）** | 「どう作るか」を実行する | ファイル生成・編集・コマンド実行・デバッグ・Git操作 |

**判断の基準：** 実装中に設計判断が必要になったら、いったん手を止めてclaude.aiに戻る。「どう実装するか」の判断はClaude Codeに任せてよいが、「何を作るか・なぜそうするか」はclaude.aiで決めてから渡す。

---

### 12.2 2つの管理ファイルと役割分担

| ファイル | 誰が読む | 何を書く |
|---|---|---|
| `docs/design.md` | 人間・Claude Code | **何を作るか・なぜそうするか**（仕様・思想・設計・ロードマップ） |
| `CLAUDE.md` | Claude Code（セッション開始時に自動読込） | **どう作るか**（コーディング規約・禁止事項・環境情報・現在地） |

この2ファイルがセットで「Claude Codeへの引き継ぎパッケージ」になる。

---

### 12.3 `docs/design.md` の更新ルール

**更新タイミング：**
- 機能を追加・変更・除外する決定をしたとき
- DBスキーマに変更が入ったとき
- ステップ・フェーズの完了条件を達成したとき（完了マークをつける）
- 未解決事項が解決したとき

**バージョン管理の方針：**  
ファイル名でのバージョン管理（`_v2.md`等）はしない。Gitのコミット履歴が自動的にバージョン管理になるため。ただしファイル冒頭の「変更履歴」セクションに、変更内容を一行で追記していく。

```md
> **変更履歴**
> - 2026-04-19 v1 初版作成
> - 2026-XX-XX Supabase接続完了、Step 1-B Phase B-1完了マーク追加
> - 2026-XX-XX anxiety_levelフィルタバグ修正、未解決事項T01をクローズ
```

### 12.4 `CLAUDE.md` の更新ルール

**更新タイミング：ステップまたはフェーズの切り替わり時に必ず見直す**

ステップ・フェーズが切り替わるとき、技術スタックや禁止事項・現在地が変わる可能性がある。そのタイミングでCLAUDE.mdを見直し、古くなった情報を更新してからClaude Codeに渡す。

また、以下の場合も随時更新する：
- 「やってはいけないこと」が新たに判明したとき（失敗の教訓）
- コーディング規約が決まったとき
- よく使うコマンドが変わったとき
- 技術スタックに変更が入ったとき

### 12.5 claude.aiスレッドを変えるときの引き継ぎ方法

claude.aiのスレッドは会話履歴が長くなると精度が下がる。新しいスレッドを開く際は以下のファイルを添付して引き継ぐ。

**引き継ぎに必要なファイル（3点セット）：**

| ファイル | 内容 | 添付方法 |
|---|---|---|
| `docs/design.md` | 仕様・思想・現状の進捗 | アップロード |
| `CLAUDE.md` | 技術スタック・禁止事項・現在地 | アップロード |
| 作業中のファイル | 直近で触っているコード（`main.py`・`database.py`等） | 必要に応じてアップロード |

**新スレッドへの引き継ぎメッセージ例：**

```
旗アプリの開発を引き継いで進めます。
添付の docs/design.md と CLAUDE.md を読んでください。

現在の状況：
- Step 1-B の Phase B-X が完了した状態です
- 次にやりたいこと：[具体的な作業内容]
- 今詰まっていること（あれば）：[内容]
```

**スレッドを変えるタイミングの目安：**
- ステップまたはフェーズの切り替わり時
- 会話が長くなって応答の精度が落ちてきたと感じたとき
- 大きく異なるテーマ（設計 → 実装、実装 → 相談 など）に切り替えるとき

---

### 12.6 ステップ切り替え時のルーティン

ステップの切り替えは「次の開発を始める前の準備セッション」として位置づける。
実装に入る前に頭を整理し、引き継ぎファイルを最新にしてからClaude Codeを起動することで、手戻りを防ぐ。

```
前のステップ完了
　↓
【claude.ai：新スレッド】
　├── design.md・CLAUDE.md を添付して引き継ぎ
　├── 前ステップの完了条件に ✅ をつける
　├── 次のステップをどういうフェーズに分けるか検討
　├── design.md の更新内容を決定
　└── CLAUDE.md の「現在の状況」の更新内容を決定
　↓
【ターミナルで】
　├── docs/design.md を更新
　├── CLAUDE.md を更新
　└── git commit -m "docs: update for Step X"
　↓
【Claude Code】
　実装開始
```

**この順番を守る理由：**
- 何を作るか曖昧なままClaude Codeに渡すと、実装途中で設計判断が必要になり手戻りが増える
- 古いCLAUDE.mdを読んだClaude Codeが間違った前提で実装を進めるリスクを防ぐ

---

### 12.7 Claude Codeへの指示の渡し方

Claude Codeを起動したら、最初に以下を伝えるのが基本パターン：

```
docs/design.md と CLAUDE.md を読んでから作業してください。
今回やりたいこと：[具体的な作業内容]
```

設計書を読ませることで、「なぜそう作るか」の文脈を共有した上で実装に入れる。

## 15. 環境変数一覧

`.env` ファイルに記載し、本番（Render）には環境変数として登録する。

```env
# ── Supabase ──────────────────────────────────
SUPABASE_URL=https://xxxx.supabase.co
SUPABASE_KEY=your-anon-key

# ── メール通知（Step 1-Bで追加） ────────────────
MAIL_FROM=noreply@yourdomain.com
MAIL_API_KEY=your-mail-service-api-key

# ── アプリ設定 ────────────────────────────────
APP_ENV=development        # development / production
```

> **セキュリティについて：** `.env` は `.gitignore` に含め、絶対にGitHubにpushしない。`.env.example` に項目名のみ（値は空白）を書いてリポジトリに含める。
